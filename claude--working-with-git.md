## Working with Git branches
- Keep the `main` or `master` branch up to date with the remote. (Note, I use `main` and `master` interchangeably below.)
- **Always create new branches off the latest HEAD**.  If I am actively working in `main` (it is "dirty") and I ask you to make a new branch, fetch `origin/main` and branch off of that.
- **Branch from `origin/master` with `--no-track`** — `git switch -c <name> --no-track origin/master`, and likewise for `checkout -b` and `worktree add -b`. Otherwise the new branch's upstream is set to `origin/master`, and because I set `push.default = upstream`, `git push -u origin <branch>` pushes to **master** rather than to the branch. Recovery: `git branch --unset-upstream`, then push with an explicit `<branch>:<branch>` refspec.
- Differentiate when you are working in a small solo project, where I am the only committer and work directly in `main`, versus a collaborative or multi-branch project, where new code should be done on branches and then merged.
- In the collaborative mode: **sync local `master` with `git fetch origin && git merge --ff-only origin/master`.** It fast-forwards, or fails loudly if the branches diverged. Prefer it to `git pull --rebase`, which quietly replays an accidental commit on `master` onto `origin/master` and reports success. Better still, don't commit directly to `master`.
- **Pulling from remote**: Prefer `git pull --rebase` over merge commits, but don't pull blindly. Before pulling, fetch and check `git log HEAD..origin/<branch> --oneline` — only pull if the remote has commits you don't have locally. After a restack/rebase, the remote typically has stale pre-restack history, and pulling would interleave master commits into the branch. In that case, force-push (`--force-with-lease`) instead.
- **Always rebase locally to bring `master` into a feature branch** — never `gh pr update-branch` (or any GitHub-side merge). A local rebase keeps history linear and ensures any new branch created off the rebased branch starts from a recent master SHA. If a rebase conflicts, resolve manually; only ask before falling back to a merge commit. **Why:** GitHub-side merges leave merge commits in the branch history, and force every downstream branch built on it to drag along an arbitrary master-merge SHA it didn't need.
- **After rebasing a branch whose commits predate a squash-merge on master, diff against master before pushing.** Git shows a conflict when your old commit and master's newer version touch the same lines. The regression comes from resolving that conflict toward your stale side: the rebase then reports success and nothing else flags it. Check with `git diff origin/master HEAD -- <files>` and ask, for each `-` line, whether your PR meant to remove it. `git blame HEAD -- <file>` settles the unclear ones — lines blamed to commits older than master's squash-merge are regressions, lines from recent follow-ups are intentional. Fix with `git checkout origin/master -- <file>`, then re-apply only your real additions.
- Prefix branches with your initials, ideally followed by a ticket ID, then a short hyphenated name — e.g. `ab_PROJ-123-fix-login`.
- **When creating Git worktrees**: put them under `~/<repo-name>-worktrees/<branch-name>`, where `<repo-name>` is the directory name of the repo's main checkout — so `~/myrepo-worktrees/<branch>` for the `myrepo` repo. Never nest one repo's worktrees inside another repo's checkout.
- **Before every commit**, run `git status` to verify all relevant files are staged — even during a multi-step workflow. Don't just `git add` the files you remember editing.
- **When modifying dependencies** (adding/removing/updating in package.json), always ensure `yarn.lock` is staged and committed too. Run `yarn install --mode=update-lockfile` if the lockfile is out of sync.
- **Never `git stash` or `git checkout` in a repo's main checkout without explicit permission.** I run multiple concurrent sessions that may each have in-progress edits on different branches — the main checkout's working branch is not yours to clobber. To read another branch's code, use `git show origin/master:path/to/file` or `git diff origin/master -- path/to/file`. To run commands against another branch, use a worktree under that repo's `~/<repo-name>-worktrees/` directory. If you're already in a worktree, do your work there and don't reach into the main checkout's branch state. Once I've explicitly authorized a stash/checkout in the main checkout for a given purpose, you can proceed with related follow-ups in that same session without re-asking — the authorization stands for the scope I named.
- To undo all uncommitted changes to a single file, use: `git checkout HEAD -- <path>`.

## Working with Github
- **Always make PRs (pull requests) drafts by default.** I mark them Ready For Review — either by hand, or by invoking a skill or workflow that does it for me. If I do invoke such a skill, then that *is* me making that call, and don't stop to ask again. Don't flip a PR to `ready` entirely on your own initiative.
- **Do not flip a PR back to Draft if it is already Ready For Review**, unless I explicitly say so. The "drafts by default" rule applies at initial creation; once a PR is Ready For Review, don't go back.
- **De-risk up front before flagging risks in the PR.** Before writing "Risks worth a careful look: X, Y, Z" in the Reviewer Guidance section, evaluate each risk and address what you can: tighten the code, swap to a more robust primitive, add a safety check, handle the error case. Only surface a risk to the reviewer when it genuinely needs their judgement (load-bearing trade-off, irreversible action, something you can't verify locally). Don't use the PR description as an externalized TODO list — a reviewer shouldn't be the first line of defense for a fix you could make yourself.
- **Run simple checks yourself - don't put them in the PR description as TODOs.** If you find yourself writing "Quick grep: `rg ...` would surface candidates" or "spot-check 20–30 sites" in the Testing / Reviewer Guidance section, run the command yourself and put the result in the PR. Consider whether a decision *requires human judgment* or can be *easily automated/executed by you*, and do the latter up front.
- **Prefer inline PR review comments over bloating Reviewer Guidance.** When a guidance note pins to a specific line or block (a raw-SQL site that bypasses an ORM hook, an ORDER BY that mirrors a specific cascade, a CTE that encodes the scope filter), post it as an inline review comment on those lines rather than listing it in the Reviewer Guidance section of the description. Reserve the Reviewer Guidance section for cross-cutting risks and observations that do not pin to any one line. If there is nothing cross-cutting, the section can be just "Risk Level: ..." with no bullets.
- **When editing/updating the description of an existing PR**, make sure to re-fetch the current description from `gh` and save it as a backup to `/tmp/pr-description-previous-<pr_num>-<timestamp>.md` in case you need to reverse it.
- **One-off plan docs should not persist permanently.** A `.plans/*.md` file added then deleted within the same PR is an artifact, not a deliverable. Delete the file before merging the PR, and link to the file at the prior SHA from the PR's Context section (build the URL with `bin/gh-link --commit=<sha> .plans/<file>.md`). Keeps the planning record accessible to anyone reading the PR later without growing the shared `.plans/` dir with stale files that don't reflect what shipped.
- When posting a comment, always prefix it with "Claude:" and a newline or two. (Make sure this doesn't break following Markdown, e.g. `Claude:\n\n# Heading` is better than `Claude:# Heading`.)
  - Exceptions to this rule are:
    a. Top-level (not inline) "command" comments — a bare `/some-command` that a bot parses — which break with the prefix.
    b. Top-level results of an agentic workflow, where the workflow's own result header has to be the first line.
  - DO put this comment on any _inline_ comment in a PR, even from an agentic workflow.
- **Posting/editing GitHub comments with `gh`**: write the body to a temp file using a single-quoted HEREDOC (`cat > /tmp/body.md << 'EOF' ... EOF`), then pass it via `--body-file /tmp/body.md` (`gh pr/issue comment`) or `-F body=@/tmp/body.md` (`gh api -X PATCH .../comments/<ID>`). Do not escape backticks — in a single-quoted HEREDOC they are already literal, and `\`` leaks into the rendered comment as a literal backslash, breaking code fences and inline code spans.
- **Don't hard-wrap lines in GitHub Markdown content** (PR descriptions, issue bodies, comments). GitHub renders Markdown with its own line wrapping; 80-char hard breaks just make the source harder to edit. Let lines flow naturally — only break for actual paragraph or list boundaries.
